# Architecture and protocol

This document describes what the code **does today**.

## Overview

```
 Client (Alice)                      Server (relay)                    Client (Bob)
 ──────────────                      ──────────────                    ────────────
 Ed25519 (disk)                      stores PUBLIC keys only           Ed25519 (disk)
 ephemeral ECDH (RAM)  ── pub ──►    routes pub + signature   ── ►     verify + TOFU
 HKDF → AES key                                                        HKDF → AES key
 AES-GCM(envelope)     ── env ──►    forwards the envelope    ── ►     validate + decrypt
```

- **Server** (`server/`): Express + Socket.IO. It keeps users and groups
  **in memory**, routes public keys and envelopes, and picks who generates the
  group key (the creator). It never performs any cryptographic operation on
  messages.
- **Client** (`client/`): all cryptography happens in
  `client/shared/websocket-client.js`, using the modules in `client/crypto/`.
  The CLI (`client/cli/`) only handles the user interface.

## Keys

| Key | Type | Lifetime | Stored in |
|---|---|---|---|
| Identity | Ed25519 | Long-term (persistent) | `client/.keys/ed25519_keypair_<user>.json` (mode 600) |
| TOFU pins | SHA-256 of each peer's Ed25519 key | Persistent | `client/.keys/pinned_keys_<user>.json` |
| Key exchange | ECDH secp256k1 | One per connection | RAM |
| 1:1 session | 16 bytes = HKDF(ECDH secret, info = sorted `"userA:userB"`) | While connected | RAM (`sharedKeys`) |
| Group | 16 random bytes generated by the creator | Until the next re-key | RAM (`groupKeys`) |

The keys directory can be changed with the `KEYS_DIR` environment variable.

## 1:1 flow

1. **Connect:** the client loads (or generates) its Ed25519 key pair,
   generates a fresh ECDH key pair, signs the ECDH public key with Ed25519 and
   sends `user_connect { username, publicKey, ed25519Pub, signature }`.
2. **`/chat Bob`:** the server sends each side an
   `exchange_public_key { targetUser, publicKey, ed25519Pub, signature }`
   carrying the other side's credentials.
3. **Verification:** each client checks the Ed25519 signature over the ECDH
   key and applies TOFU:
   - on first contact, it stores the fingerprint;
   - if the fingerprint later changes, it **rejects** the connection (MITM
     alert).
4. **Derivation:** secret = ECDH(priv, peerPub); `encKey` =
   HKDF-SHA256(secret, info = sorted names, 48 bytes)[0..16]. The remaining 32
   bytes (`authKey`) are reserved and currently unused.
5. **Messages:** every message becomes a v1 envelope (below), sent with
   `send_message` and delivered to the recipient as `message_received`.

## v1 envelope

```json
{ "v": 1, "ts": 1732420000000, "from": "Alice", "to": "Bob", "isGroup": false,
  "nonce": "<12 bytes hex>", "ct": "<ciphertext hex>", "tag": "<16 bytes hex>" }
```

- AES-128-GCM with a random 96-bit nonce.
- **AAD** = `v ‖ ts ‖ from ‖ to ‖ nonce`, so tampering with any metadata
  invalidates the tag.
- On receipt, the client checks, in this order:
  1. required fields and version;
  2. `|now − ts| ≤ 5 min`;
  3. that `from` is the expected sender;
  4. that the nonce has not been seen before;
  5. the GCM tag.

  The nonce is only added to the cache **after** the tag has been verified.

## Group flow

1. `/group G`: if the group does not exist, the user becomes its **creator**.
2. When someone joins, the server routes `exchange_public_key` (with
   `isGroup: true` and `groupName`) between the new member and every existing
   member. Each pair derives a pairwise key, as in the 1:1 flow.
3. About 1 s later, the server sends `generate_and_distribute_group_key` to
   the creator. The creator generates 16 random bytes, encrypts them for each
   member in an envelope under that member's pairwise key, and sends
   `distribute_group_key { encryptedKeys: [{ member, encryptedKey }] }`.
4. The server delivers each envelope (`group_key_received`). It cannot open
   them.
5. Group messages use the same envelope with `to = group name` and are
   delivered to every online member (`group_message_received`).
6. **Leaving** (`/leave` or disconnecting): the member who left deletes the
   group key. If the creator left, another member takes over. A **new** key is
   generated and distributed to the remaining members, so the former member
   cannot read future messages. If only one member remains, the key is
   discarded.

## Socket.IO events

| Client → server | Server → client |
|---|---|
| `user_connect`, `start_chat`, `send_message`, `join_group`, `leave_group`, `distribute_group_key`, `leave_chat`, `list_users`, `list_groups` | `user_connected`, `user_joined`, `user_left`, `chat_started`, `chat_ready`, `chat_left`, `exchange_public_key`, `message_received`, `group_message_received`, `group_joined`, `group_left`, `member_joined_group`, `member_left_group`, `generate_and_distribute_group_key`, `group_key_received`, `clear_group_key`, `users_list`, `groups_list`, `error` |

HTTP routes: `GET /`, `GET /status`, `GET /info`.

## Known limitations

These are the weaknesses of a teaching protocol. They are worth studying
because they are exactly what real systems (Signal, MLS) solve.

1. **First contact trusts the server.** TOFU only detects an identity change
   *after* the first contact. A malicious server can hand out a fake Ed25519
   key the very first time, and there is no out-of-band verification (such as
   comparing fingerprints in person or with a QR code).
2. **No authentication on the server.** Any client can register with any name
   that is not already taken.
3. **AAD without delimiters.** The fields are concatenated with no separator
   or length prefix, so `from="ab", to="c"` and `from="a", to="bc"` produce
   the same AAD. The practical impact is small because the key already binds
   the pair, but the right fix is a length-prefixed (TLV) or canonical JSON
   encoding.
4. **The recipient does not check `to`.** Protection comes only from the key
   being unique to the pair or group.
5. **Anti-replay is in memory only.** After a client restart, an envelope
   from the last 5 minutes could be accepted again.
6. **No ratchet.** The session key lasts for the whole connection. Forward
   secrecy only exists between connections (ECDH is regenerated on every
   `connect`), not per message as in the Double Ratchet.
7. **The group creator is a trust point.** The creator chooses the key, and
   the server decides who the creator is.
8. **Fixed-delay races.** `chat_ready` (500 ms) and group key generation (1 s)
   rely on `setTimeout` rather than acknowledgements from the clients.
9. **Teaching choices:** `/keys` and `--debug` print private and session
   keys, and the server's CORS policy is open (`*`).
10. **The curve is secp256k1.** It works, but X25519 is today's standard
    choice for ECDH.
